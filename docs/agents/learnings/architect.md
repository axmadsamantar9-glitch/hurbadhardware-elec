# Architect Learnings

## Template/Config Tables Should Stay Loosely Coupled to the Data They Inform

**Symptom:** product-planning's investigation for HUB-27 recommended a strict FK from `ProductSpec.specTemplateKeyId` to a new per-category template table, reasoning that zero backfill risk meant "why not enforce integrity now."
**Cause:** Zero backfill risk only argues that the _migration_ is cheap, not that the _relationship_ is right. A strict FK on ProductSpec would force every spec value to reference a category template row, which breaks the moment (a) a product needs a genuine one-off spec not in the template, or (b) an admin edits/retires a template key and now every product spec that pointed at it needs a migration decision. Templates are meant to _evolve independently_ of already-entered product data.
**Rule going forward:** When a new "template" or "suggested values" table is proposed to firm up an existing free-text field, default to a loose/informational relationship (new table has no FK _from_ the existing data; it's read by the UI layer to prefill/suggest) unless the PRD explicitly requires every value to be drawn from a closed set. Reserve strict FKs for genuinely closed enumerations (e.g., Order -> OrderStatus), not admin-editable "typical values" tables. Use a stable `slug`-style identity field (not the translatable `*_en` field) for any uniqueness constraint on bilingual template rows, matching the Category/Brand/Product `slug` convention.

## `prisma migrate diff` Always Emits False Drift on the Manual `search_vector` Column

**Symptom:** Every `prisma migrate dev --create-only` run against the current schema (HUB-27, HUB-28) emits `DROP INDEX "products_search_vector_idx"` and `ALTER COLUMN "search_vector" DROP DEFAULT`/`ADD COLUMN "search_vector" tsvector` noise in the generated migration, even when the actual model change has nothing to do with search.
**Cause:** `Product.searchVector` is declared as `Unsupported("tsvector")?` because it's a Postgres `GENERATED ALWAYS AS (...) STORED` column managed by raw SQL (`prisma/manual-sql/001_search_vector.sql`, `003_brand_name_cache_sync.sql`) outside Prisma's schema. Prisma can never fully reconcile an `Unsupported` column against the live DB, so every diff re-proposes touching it.
**Rule going forward:** After `prisma migrate dev --create-only`, always inspect the generated `migration.sql` for these two false-drift statements and manually strip them before committing (leave the generated column and its GIN index untouched) — same as the precedent in `20260829140300_drop_product_brand_column/migration.sql`. Never let `migrate dev` actually _apply_ this drift to a live DB. Document the omission with a comment pointing at this file so the next migration doesn't get "fixed" back in.

## New Nullable Columns on `Product` Still Break Fixture-Shaped Test Mocks

**Symptom:** Adding two new nullable columns to `Product` (`compatibilityWarningEn/So` for HUB-28) caused `tsc --noEmit` to fail across every test in `src/lib/api/products.test.ts`, even though the columns are optional at the DB level.
**Cause:** Prisma's generated `Product` type has no optional fields for nullable columns — `T | null` is still a required key. Hand-written object-literal test fixtures (`mockProduct = { ... }`) are structurally checked against that type, so a schema addition always requires touching every fixture, not just call sites that read the new field.
**Rule going forward:** When a schema change adds columns to a model with existing hand-written fixture objects in test files, budget a quick sweep of `tsc --noEmit` after `prisma generate` and patch shared fixtures directly (usually one `mockX` object touches every test in the file) rather than assuming "nullable = no test fallout." This is in scope for the architect to fix inline when it's a one-line mechanical addition to a shared fixture — don't leave the repo red for the next agent to discover.
